# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

# stickly

A notes/reminders app organized on a whiteboard-style weekly board, with Google Calendar integration (see README.md for the functional and stack overview).

**Next.js 16 has breaking changes vs. older versions** (see `AGENTS.md`): read the relevant guide in `node_modules/next/dist/docs/` before writing Next-specific code, and heed deprecation notices. `next dev` re-adds that block to `AGENTS.md` automatically.

## Commands

- `npm run dev` — start the dev server.
- `npm run build` / `npm run start` — production build / start.
- `npm run lint` — ESLint (flat config, `eslint.config.mjs`).
- `npm run type-check` — `next typegen && tsc --noEmit`; regenerates Next's route types before checking.
- `npm test` — Vitest (jsdom environment, `tests/**/*.test.{ts,tsx}`). Run a single file with `npm test -- tests/lib/notes.test.ts`, or filter by name with `npm test -- -t "pattern"`.
- `npx prisma migrate dev` — apply/create Prisma migrations locally.
- `npm run db:seed` — runs `prisma/seed.sql` (idempotent; demo users `@stickly.test`, credentials login only, passwords in the file header).
- `npx prisma generate` — regenerate the Prisma client into `src/generated/prisma` (runs automatically via `postinstall`).
- Deploy is Vercel: `vercel-build` runs `prisma migrate deploy` before `next build`. CI (`.github/workflows`) runs lint, type-check, test and build on every push/PR.
- Env vars are documented in `.env.example` (`DATABASE_URL`, `AUTH_SECRET`, Google OAuth client, `GOOGLE_TOKEN_ENCRYPTION_KEY`, `GOOGLE_GENERATIVE_AI_API_KEY`, optional `CHAT_MODEL`; optional `SITE_URL` for absolute metadata URLs and QStash's delivery URL, defaulting to Vercel's production domain; `VAPID_*` for push notifications; `QSTASH_*` (or `QSTASH_DEV="true"` locally) and `CRON_SECRET` for reminders).
- A project `Stop` hook (`.claude/hooks/verify.sh`) runs lint + type-check + tests at the end of each turn when `src`, `tests`, `prisma`, `messages` or the tooling config changed, and feeds failures back (up to 3 attempts) — so there's no need to run those manually just before finishing.

## Architecture

- **Server actions, not API routes.** All mutations live in `src/app/actions/*.ts` (`"use server"`), called directly from client components. The only route handlers are Auth.js's, the WhatsApp webhook (`src/app/api/whatsapp/route.ts`, see **WhatsApp chat**), which Meta calls, and the two reminder routes (`src/app/api/reminders/`, see **Push notifications and reminders**), which Vercel Cron and QStash call. Every action starts by resolving the current user via `requireUserId()` (`src/lib/session.ts`), which throws `UNAUTHORIZED` if there's no session, and ends by revalidating the page it changes (`revalidatePath("/")` for the board, `"/profile"` for profile-only data; the push and WhatsApp code actions change nothing server rendered and skip it).
  - Errors are thrown as bare string codes (`new Error("TITLE_REQUIRED")`) that the UI translates via the `errors` namespace in `messages/*.json` — when adding a new code, add the key to both `en.json` and `es.json`.
  - Pure validation/transform logic is pulled out into `src/lib/*` (e.g. `profile.ts`, `notes.ts`, `noteInput.ts`, `webChat.ts`) so it can be unit-tested without Prisma.
  - `notes.ts`: CRUD + reordering/moving notes and the draft notes (`createDraftNote`, `updateDraftNote`, `moveDraftNote`, `scheduleDraftNote`). `createNote` and `createDraftNote` delegate to `createNoteForUser` / `createDraftNoteForUser` (`src/lib/noteCreation.ts`), which takes an already-resolved `userId` and so lives outside `"use server"` files on purpose (every export there becomes a callable action).
  - `calendar.ts`: `addNoteToGoogleCalendar` creates/updates the linked Google Calendar event for a note (`googleEventId`); the event body is built by `toCalendarEvent` (`src/lib/calendarEvent.ts`). After that, `notes.ts` keeps the event in step on its own: deleting it when a note is deleted or loses its time (`deleteCalendarEvent`, also in `after()`), and updating it when `updateNote`/`moveNote` change what it shows (`updateCalendarEvent`, run in `after()` so saving or dragging never waits on Google; it re-reads the note and unlinks it if the event was deleted from Calendar). Both live in `src/lib/googleCalendar.ts` and are best-effort (never throw, log failures).
  - `profile.ts`: user profile fields, password change, and `updateTimeZone` (called by `TimeZoneSync`, see **Time zones**).
  - `chat.ts`: `sendChatMessage`, the assistant chat (see **Assistant chat** below).
  - `whatsapp.ts`: `createWhatsAppLinkCode` / `unlinkWhatsApp`, used by the profile (see **WhatsApp chat** below).
  - `push.ts`: `savePushSubscription` / `deletePushSubscription` / `sendTestNotification`, and `reminders.ts`: `updateReminderSettings` (see **Push notifications and reminders**). Like the WhatsApp code action, the push ones don't revalidate: the device's state lives in the browser.
  - `locale.ts`, `theme.ts`: only write the `NEXT_LOCALE` / `THEME` cookies (theme falls back to the OS preference when the cookie is unset, see `src/lib/theme.ts`).
- **Auth (`src/auth.ts`).** Auth.js with two providers: Google (primary, grants the Calendar scope) and Credentials (email/password against a bcrypt `password` hash on `User`; the password is set from the profile page via `setPassword` — not mentioned in the README's feature list). On a Google sign in, the `jwt` callback upserts the app's `User` row and stores the Google tokens on it (`saveGoogleTokens`); the JWT only carries `userId`, plus how and when the session signed in (`authProvider`, `authAt`, set on every sign in and kept on refresh).
  - **Password reset via Google.** Changing an existing password needs the current one, unless the session signed in with Google within `RECENT_SIGN_IN_MS` (10 min, `isRecentGoogleSignIn` in `src/lib/session.ts`): that's how a Google user resets a forgotten password. The profile's "Forgot it?" link (shown when the user has a `googleId`) calls `confirmPasswordResetWithGoogle`, which signs in with Google again and returns to `/profile?password=reset` with the form open and the current-password field hidden. `authProvider`/`authAt` reach the server through the `session` callback and are in `PRIVATE_SESSION_FIELDS`, so the browser never gets them. There's no email-based reset: credentials-only users can't recover a forgotten password.
  - **Google tokens live on `User`, encrypted** (`googleRefreshToken`, `googleAccessToken`, AES-256-GCM with `GOOGLE_TOKEN_ENCRYPTION_KEY`, `src/lib/tokenCrypto.ts`; plus `googleAccessTokenExpiresAt`), so a password session of the same user can use Calendar too. They're read and written through `src/lib/googleTokens.ts`: `auth.ts` saves them on sign in, and only `googleCalendar.ts` should read them. Every Calendar call goes through `withGoogleCalendar(userId, fn)` (`src/lib/googleCalendar.ts`): it uses the stored access token, refreshes it a minute before it expires, retries once on a 401, and when Google revokes the refresh token (`invalid_grant`) clears the tokens and throws `GOOGLE_RECONNECT_REQUIRED` (only a new Google sign in fixes that). Refresh failures are logged with Google's response. A missing encryption key doesn't block sign in: it's logged and Calendar asks to reconnect.
  - The session holds no secrets, but `src/app/api/auth/[...nextauth]/route.ts` still wraps Auth.js's handlers to strip `PRIVATE_SESSION_FIELDS` (`src/lib/publicSession.ts`, which keeps the old `accessToken`) from `/api/auth/session` as a safeguard. Any new server-only session field goes in that list.
  - Credentials login lives in `src/lib/credentials.ts`: emails are normalized (trim + lowercase), lookup is case-insensitive for legacy rows, and a dummy bcrypt hash is compared when the user doesn't exist so timing doesn't reveal which emails have accounts.
- **Security headers.** `src/proxy.ts` (Next 16's replacement for `middleware.ts`) sets a per-request nonce-based CSP built by `src/lib/securityHeaders.ts`; the static headers (HSTS, X-Frame-Options, etc.) are applied in `next.config.ts`. Loading anything from a new external origin (images, scripts, form redirects) requires adding it to the CSP directives there.
- **Data access.** No repository layer — server actions call `prisma` (`src/lib/prisma.ts`) directly. Multi-step mutations that touch note ordering (`moveNote`, `moveDraftNote`, `scheduleDraftNote`) run inside `prisma.$transaction`; `createDraftNoteForUser` additionally takes a Postgres advisory lock (`pg_advisory_xact_lock`) keyed on `userId` to make the draft limit's count-then-create race-safe across concurrent calls (two tabs, the chat).
- **Note ordering.** Notes within a day are ordered by an integer `position` column, manipulated via `insertAtIndex` (`src/lib/ordering.ts`) rather than fractional indexing; moving a note reassigns `position` for every note in the affected day. A new note takes the user's highest `position` + 1 (not per day, since a `TIMED` note's local day depends on the zone), which still puts it last in its day. Drafts are ordered among themselves by their own `position`s; `scheduleDraftNote` gives a draft its position in the day it's dropped on.
- **Week/date handling.** `src/lib/week.ts` computes week ranges (Monday-start, `[start, end)`), parses/formats the `week` query param, and steps to adjacent weeks — no week number is stored, see below. `src/lib/datetime.ts` converts between `yyyy-MM-dd` days and their `Date` at 00:00 UTC.
- **Time zones.** Notes are stored in UTC (see the schedule decision below) and shown in the user's zone, `User.timeZone`: `TimeZoneSync` (mounted in `page.tsx`) stores the browser's zone via `updateTimeZone` when it differs and refreshes, and `getUserTimeZone` (`src/lib/userTimeZone.ts`) falls back to Vercel's `x-vercel-ip-timezone` header, then UTC.
  - `src/lib/schedule.ts` is the only place that converts (no server imports, so the board uses it too): `toStoredSchedule` (local day + time → stored), `toLocalSchedule` (stored → local), `localDaysFilter` (Prisma conditions for a range of local days), `parseScheduleInput` (validates what the client sends).
  - The board does the conversion: `page.tsx` passes the week's notes as stored (`StoredNoteDTO`) plus the zone, `Board` groups them into local days (`groupNotesByDay`, `src/lib/noteGroups.ts`) and provides the zone to `NoteForm` (`TimeZoneContext`), and the forms/drag & drop send a stored schedule to `createNote`/`updateNote`/`moveNote`. The server still needs the zone for the week query, "today" and which notes share a local day when reordering. The chat converts on the server, with the zone the browser sends with each message.
  - Server code must never derive a day from the process time zone (Vercel runs in UTC, local dev doesn't); Vitest pins `TZ=Pacific/Kiritimati` to catch that.
- **Board UI (`src/components/board/`).** `Board.tsx` is the top-level client component; drag & drop between days/positions is handled with `@dnd-kit` (mouse, touch with a short press on the handle, and keyboard sensors). `useNoteEditor.ts` holds what `NoteForm.tsx` and `DraftForm.tsx` share: the fields being written, the note's id and the keyboard and outside-click behavior (Enter or clicking outside saves, Escape cancels, Shift+Enter adds a line break). Every board mutation goes through `run` (`BoardActionsContext.tsx`): it shows the result at once with `useOptimistic` (new notes as pending entries in `Board`), React undoes it if the action throws, and the error code shows as a notice above the board instead of the error page. No action is followed by `router.refresh()`: `revalidatePath` already returns the re-rendered board in the action's response.
- **App-level pages and metadata.** `src/app/not-found.tsx` (root 404, inside the root layout so it gets the theme and locale), `loading.tsx` skeletons for the board and the profile (`role="status"` + `sr-only` text, `motion-safe:animate-pulse`), and the metadata: `generateMetadata`/`generateViewport` in `layout.tsx` (localized description, title template, `themeColor` from the `THEME` cookie; URL and colors in `src/lib/siteMetadata.ts`), `opengraph-image.tsx` and `apple-icon.tsx` next to `icon.tsx`, all static and in English (built once).
- **i18n.** `next-intl`, locale resolved from a cookie (`NEXT_LOCALE`, `src/i18n/locales.ts`/`request.ts`) rather than the URL; supported locales are `en`/`es` with message catalogs in `messages/*.json`.
- **Assistant chat.** `ChatWidget.tsx` (`src/components/chat/`, mounted in `page.tsx` outside `<Board>` so it survives week navigation) sends the whole conversation to `sendChatMessage`, which authenticates, sanitizes and consumes the quota, then hands the turn to `runChatTurn` (`src/lib/chatAssistant.ts`, outside `"use server"` so other channels can share it). `runChatTurn` calls Gemini through the Vercel AI SDK v7 (`ai` + `@ai-sdk/google`; model from `CHAT_MODEL`, default in `src/lib/webChat.ts`) with three tools: `create_note`, `create_draft_note` (only when the user explicitly asks for a draft; a missing date makes the model ask for it) and the read-only `list_notes`.
  - Tool definitions (`CREATE_NOTE_TOOL`, `CREATE_DRAFT_NOTE_TOOL`, `LIST_NOTES_TOOL`) and their parsers live in `src/lib/noteInput.ts`. Tool arguments are untrusted JSON: always run them through `parseNoteToolInput` / `parseDraftNoteToolInput` / `parseListNotesInput`, never trust the schema.
  - The AI SDK feeds anything thrown from a tool's `execute` back to the model verbatim, so tools must not throw: `toolErrorResult` returns recoverable input codes (e.g. `DAY_REQUIRED`) to the model and replaces unexpected errors with a generic code after logging them.
  - The conversation lives only in the widget's state (not persisted, lost on reload); the server re-validates and trims it on every turn (`sanitizeChatMessages`). The model resolves relative dates from `getUserToday` (user's time zone from the browser, plus the Monday–Sunday board week), and `list_notes` returns every day of the range, including empty ones.
  - Rate limiting (`consumeChatQuota`, limits in `CHAT_LIMITS`): one `WebChatUsage` row per message, rolling windows per user and global, insert-then-count, rejected messages don't count. Sized for Gemini's free tier, whose quota is per API key; the key's Cloud project has no billing account so going over it fails with 429 (`CHAT_QUOTA_EXCEEDED`) instead of charging. `maxRetries: 0` so a 429 doesn't burn more quota.
  - A 503 ("high demand") is retried once with `CHAT_FALLBACK_MODEL` (optional), only if no note was saved yet in that message. If a note was saved and the model then fails, `runChatTurn` returns the notes with an empty reply instead of throwing, so the user doesn't resend the message and duplicate them. `runChatTurn` doesn't revalidate: `sendChatMessage` calls `revalidatePath("/")` when notes were created (the WhatsApp path runs in `after()` and the board is dynamic anyway).
  - Tests: `tests/actions/chat.test.ts` drives the real tool loop with `MockLanguageModelV4` (`ai/test`) by mocking `@ai-sdk/google`; component tests (`tests/components/`) render inside `NextIntlClientProvider` with `messages/es.json`.
- **WhatsApp chat.** Users message a WhatsApp number (Meta Cloud API) and get the same assistant: same `runChatTurn`, tools, quota (`WebChatUsage`) and Gemini key as the board's chat.
  - `src/app/api/whatsapp/route.ts`: `GET` answers Meta's one-time verification (`WHATSAPP_VERIFY_TOKEN`); `POST` checks `X-Hub-Signature-256` against the raw body with `WHATSAPP_APP_SECRET` (`src/lib/whatsappWebhook.ts`), answers 200 right away and handles the messages in `after()` (`maxDuration = 60`), because Meta retries slow webhooks and a model turn can take ~20 s.
  - `handleInboundMessage` (`src/lib/whatsappInbound.ts`) first records the message's `wamid` in `WhatsAppInboundMessage` and skips ids it already has (Meta delivers at least once). It's recorded before handling on purpose: a failure drops the message rather than risking a second note. A message that is only a 6-digit code links the number; an unlinked number or a non-text message gets a fixed reply without calling the model; anything else from a linked number goes to the assistant.
  - Linking: the profile (`WhatsAppLink.tsx`, shown only when `WHATSAPP_DISPLAY_NUMBER` is set) gets a code from `createWhatsAppLinkCode`, stored in `WhatsAppLinkCode` as an HMAC keyed with `AUTH_SECRET` (`src/lib/whatsappLink.ts`) so the webhook can look it up. Consuming it (`linkNumber`) deletes the code first inside the transaction, so a code links at most once, and sets `User.whatsappNumber` (E.164 digits as Meta sends them in `from`), moving the number off any other user. Code attempts are limited per sending number (`isLinkAttempt` rows, `MAX_LINK_ATTEMPTS_PER_HOUR`).
  - The conversation is persisted (`WhatsAppMessage`, unlike the board's chat): the latest `MAX_HISTORY_MESSAGES` turns within `HISTORY_IDLE_MS` (30 min) are sent with each message, so the assistant can ask for a missing date. Only successful turns are stored. Expired turns are pruned for every user whenever any message arrives (`recordInbound`, next to the one-day prune of inbound ids), so an idle user's conversation doesn't linger; no cron. The time zone is `User.timeZone` and the prompt gets `locale: null` (reply in the user's language). Fixed replies (`WHATSAPP_REPLIES`) are bilingual, since an unlinked number has no user or locale.
  - Replies are capped at `MAX_ASSISTANT_MESSAGE_LENGTH`, cut at the last line break by `truncateReply` (a single day's notes come back in detail, one block per note, so a long day loses whole notes rather than ending mid-sentence), and go through `sendWhatsAppText` (`src/lib/whatsappApi.ts`, best-effort). Meta reports Argentine/Mexican mobiles as `549…`/`521…` but only delivers replies to `54…`/`52…`, hence `toReplyNumber`.
  - Local testing needs a tunnel (ngrok; `allowedDevOrigins` in `next.config.ts` lets `*.ngrok-free.app` through) set as the webhook URL in Meta. The Meta app must also be subscribed to the WhatsApp Business Account (`POST /{WABA_ID}/subscribed_apps`), or no messages arrive even with the webhook configured.
- **Push notifications and reminders.** Web Push to every device where the user turned notifications on, managed from the profile.
  - **Installable app (PWA, no offline support):** `src/app/manifest.ts`, icons from `apple-icon.tsx` (opaque, full-bleed yellow, also the manifest's maskable icons, 180/192/512 via `generateImageMetadata`) and `icon.tsx` (transparent; favicon and notification icon). `public/sw.js` only shows pushes and opens the app on a tap (no caching). The CSP allows `worker-src`/`manifest-src 'self'`, `proxy.ts` skips both files, and `next.config.ts` serves `sw.js` uncached. `InstallPromptListener` (root layout) keeps Chromium's `beforeinstallprompt`, used by the profile's install section (`InstallApp.tsx`, phones only, hidden once installed); iOS gets the Share menu steps.
  - **Devices:** `PushSubscription` (one row per browser endpoint; `locale` so background sends can translate, via `getNotificationTranslator`). The endpoint must be on the push services' allowlist (`src/lib/pushSubscription.ts`, the server POSTs to it). `NotificationSettings.tsx` + `pushDevice.ts` (browser APIs, mocked in tests) turn it on/off per device; the profile re-saves an active subscription on open. `SignOutForm` turns the device off before signing out. Sending is `sendPushNotification` (`src/lib/webPush.ts`): never throws, deletes subscriptions the push service reports gone (404/410).
  - **Reminders:** per user, all in the profile (`ReminderPreferences.tsx`): `User.reminderMinutesBefore` (null = off; options in `REMINDER_LEAD_MINUTES`) for TIMED notes, and a daily digest (`digestEnabled`, `digestTime` local, default 07:00) listing the day's pending notes. ALL_DAY notes only appear in the digest.
  - **Delivery:** QStash (`src/lib/qstash.ts`) delivers each reminder at its time to `POST /api/reminders/deliver` (signature checked); a daily Vercel Cron (`vercel.json`, `GET /api/reminders/schedule`, `CRON_SECRET` bearer) queues the next 48 h (`REMINDER_QUEUE_WINDOW_MS`) in batches. Saving changes queues right away in `after()`: `createNoteForUser` (board, web chat and WhatsApp), `updateNote`/`moveNote` when the time changes, `toggleNoteDone` back to pending, `updateReminderSettings`, `updateTimeZone`, and a device new to the user. All of it is in `src/lib/reminders.ts`.
  - **Nothing queued is ever cancelled.** `deliverReminder` re-reads the note/user and drops what no longer applies (the reminder instant or digest instant no longer matches, done, deleted, setting off, no device, over `MAX_REMINDER_DELAY_MS` late), then claims it with a conditional `updateMany` (`Note.reminderSentFor` = the instant sent, `User.digestSentOn` = the local day) before pushing, so a duplicate or retried delivery never pushes twice (a failure loses it rather than sending twice). Turning the digest on or moving its time clears `digestSentOn`, so today's can go out again. QStash dedup ids include the delivery instant, which is safe because a delivered instant is in the past and never queued again.
  - Local testing: `QSTASH_DEV=true` (the SDK starts QStash's dev server on :8080, which calls `localhost:3000`); no tunnel needed.
- **Tests.** No test database: action tests (`tests/actions/`) mock `@/lib/prisma`, `@/auth` and `next/cache` with `vi.hoisted` + `vi.mock` (including `$transaction`/`$executeRaw`), then import the action under test.
- **Prisma client.** Generated into `src/generated/prisma` (not `node_modules`), via the `prisma-client` generator and `@prisma/adapter-pg` as the driver adapter — see `prisma7.config.ts` for the config used by the CLI.

## Design decisions to respect

- After changing server actions, `schema.prisma`, `src/auth.ts`, ordering/week logic or the board, delegate a review to the `stickly-reviewer` subagent before finishing.
- A note's schedule is `startsAt` (`timestamptz`) + `kind`, the same split Google Calendar and iCalendar use (`dateTime` vs `date`). `TIMED`: an instant in UTC, shown in the viewer's zone (10:00 written in Buenos Aires shows 09:00 in Miami), synced to Calendar as that instant. `ALL_DAY`: a day stored as its 00:00 UTC and read in UTC, never converted, so it stays on its day everywhere (converting it was the original "board shows tomorrow" bug). Only `TIMED` notes can be synced to Calendar.
- `title` and `location` are kept separate because the Calendar API accepts `location` as its own event field.
- `startsAt` is nullable; the only valid case with `null` is a draft note (`isDraft: true`).
- A user can keep at most `MAX_DRAFT_NOTES` (4, in `src/lib/noteInput.ts` so the board can read it too) drafts. The limit is enforced at the application level, not in the schema: every draft is created through `createDraftNoteForUser`, which counts the user's drafts under the advisory lock before creating one (`DRAFT_LIMIT_REACHED`). Board and chat share it, so neither can go over the limit.
- Composite index `[userId, startsAt]` is meant for the most frequent query: a user's notes between the start and end of a given week.
- Week navigation is resolved via query (`localDaysFilter`: the week's local midnights in UTC for `TIMED` notes, the plain days for `ALL_DAY` ones); no week number is persisted on the note — it's derived on each query.
- `@auth/prisma-adapter` is not used: the schema has no `Account`/`Session` models. Sessions are JWT-based (`src/auth.ts`); the Google tokens are stored encrypted on `User` (not in the JWT, which is per session and would leave password sessions without Calendar). The app's own `User` record is synced (upserted) in Auth.js's `jwt` callback.
- Notes created from the chat (board or WhatsApp) are not synced to Google Calendar automatically; syncing stays a manual per-note action.
- Reminders go through QStash, not a frequent cron, on purpose: Vercel Hobby only allows a daily cron, and polling every few minutes would keep Neon's free-tier compute awake all month. Don't replace it with polling. Everything about notifications is configured from the profile; notes have no per-note reminder control (rejected as redundant clutter).
- The WhatsApp bot only replies (inside Meta's 24 h window); it never starts a conversation, since that needs Meta-approved templates and is billed separately.
- WebMCP (exposing the tools to external browser agents via `document.modelContext`) was prototyped and deliberately removed; the chat talks to the server only. Don't reintroduce it without asking.
- Postgres runs on the user's local server (not Docker). The dev database is `stickly-development`, following the `<app>-development`/`<app>-test` convention used in their other projects.

## Broader plan context

This project is being developed alongside another, bigger personal project (a social network, with a Rails API, a React client, and a Node.js messaging service), also intended as a portfolio piece. stickly serves as a "quick win" block: a smaller, well-scoped project to make progress on during moments with less time or energy available.
